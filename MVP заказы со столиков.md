# MVP: заказы со столиков

Oct 8, 2026 · @Sem

## Цель

Гость сканирует QR на своём столе, выбирает позиции и отправляет заказ. Заказ сразу появляется в iikoFront на нужном столе, бариста работает с ним на кассе как обычно. Всё должно стабильно работать на 21 человека один вечер.

Допущения: онлайн-оплаты нет, гости платят на кассе как обычно. iiko — источник меню и столов, и туда же уходит каждый заказ: он появляется в iikoFront на нужном столе (проверено 8 окт., заказы № 516–517 дошли до кассы).

Решение (8 окт.): своей панели заказов у бариста нет — заказы ведут в iikoFront. У нас остаётся только стоп-лист.

Решение (8 окт.): гость при входе вводит имя, и оно попадает в чек iiko комментарием. У заказа на стол в iiko нет общего комментария, поэтому имя (и пожелание гостя) пишется в комментарий каждой позиции: `Саша · без сахара`, до 255 символов.

## Сценарии

Гость заказывает со своего телефона; бариста видит заказы в iikoFront, а на нашем сайте только ведёт стоп-лист.

### Гость

1. Сканирует QR и попадает на `/t/{table_token}`. Вводит своё имя (запоминается на телефоне), видит название стола и меню.
2. Добавляет позиции; у блюд с модификаторами (молоко, сироп, вид чая) выбирает их в отдельном окне. При желании пишет комментарий («без сахара») и отправляет. Имя и комментарий уходят в чек iiko.
3. Видит карточку заказа: «Передаём на кассу…» → «Принят — готовим» и крупно номер заказа из iikoFront («№518, назовите на кассе»). Если касса не приняла заказ — «Не дошёл до кассы — подойдите к бариста».
4. Может отправить ещё один заказ, это будет новый отдельный заказ.

### Бариста

1. Заказы видит и ведёт в iikoFront: стол, позиции с модификаторами, имя гостя в комментарии. Гость на кассе называет номер заказа iiko.
2. На `/bar?key=...` — только стоп-лист: переключатель у каждой позиции, поиск. Выключенная позиция сразу пропадает у гостей.

## Стек

Минимум движущихся частей: один процесс, один файл БД, фронт без сборки.

- FastAPI, uvicorn **строго с одним воркером**: лимит частоты заказов живёт в памяти процесса.
- SQLite (через aiosqlite или SQLAlchemy async). Для одного вечера этого хватает, и бэкап сводится к копированию файла.
- Фронт: Jinja2-шаблоны и немного vanilla JS. Без сборки, мобильная вёрстка.
- Гость опрашивает статус своего заказа раз в 5 секунд, пока заказ едет на кассу.
- `qrcode[pil]`, чтобы сгенерировать PNG для каждого стола.

## Модели

Четыре таблицы. В `OrderItem` цена и название сохраняются снимком, чтобы правки меню не меняли уже принятые заказы.

| Модель | Поля |
| --- | --- |
| `Table` | `id`, `name` («Зал · Стол 3», как на кассе), `token` (случайная строка, она и идёт в QR), `iiko_table_id` |
| `MenuItem` | `id`, `name`, `price`, `category`, `is_available`, `sort`, `iiko_product_id`, `sku`, `description`, `image_url`, `modifiers` (JSON групп из iiko) |
| `Order` | `id`, `table_id`, `guest_name`, `comment`, `created_at`, `updated_at`, `iiko_status` (`off` / `sending` / `sent` / `error`), `iiko_order_id`, `iiko_number` (номер в iikoFront), `iiko_error`; колонка `status` осталась от панели бариста и не используется |
| `OrderItem` | `order_id`, `menu_item_id`, `qty`, `price_snapshot`, `name_snapshot`, `modifiers` (JSON-снимок выбранных) |

## API

Гость работает по токену стола. Все запросы бариста идут с `key`, который лежит в env.

### Гость

| Метод и путь | Что делает |
| --- | --- |
| `GET /t/{token}` | Страница стола; 404, если токен неизвестен |
| `GET /api/menu` | Только доступные позиции |
| `POST /api/orders` | Тело `{table_token, guest_name, items: [{menu_item_id, qty, modifiers: [{id, amount}]}], comment}`. Проверить, что позиции доступны, `qty` от 1 до 10, позиций не больше 20, модификаторы укладываются в min/max групп iiko |
| `GET /api/orders/{id}?token=...` | Статус отправки на кассу и номер iiko. Токен стола нужен, чтобы чужие заказы нельзя было смотреть перебором id |

### Бариста

| Метод и путь | Что делает |
| --- | --- |
| `GET /bar` | Страница стоп-листа |
| `GET /api/bar/menu` | Все позиции, включая выключенные |
| `PATCH /api/bar/menu/{id}` | Тело `{is_available}`: стоп-лист |

## iiko

Авторизация: `POST /api/v2/access_token` с `apiKey`, `appId`, `clientSecret`, токен живёт час.

**Меню и столы** забирает скрипт `import_menu.py`: внешнее меню (`/api/2/menu/by_id`; номенклатура у нас пустая), столы (`/api/1/reserve/available_restaurant_sections`), id организации и терминальной группы.

**Заказы** уходят фоном после сохранения в SQLite: `POST /api/1/order/create` на `tableIds: [iiko_table_id]`, затем опрос `/api/1/commands/status` до `Success` и `/api/1/order/by_id` за номером заказа. Модификаторы идут в `items[].modifiers`, у групповых обязателен `productGroupId`. Каждый заказ гостя — отдельный заказ в iiko. Без `IIKO_SEND_ORDERS=true` заказы никуда не уходят — флаг только для разработки.

Если iiko не принял заказ, автоповтора нет (касса могла принять, но не успеть подтвердить — повтор дал бы дубль): гость видит «подойдите к бариста», заказ остаётся в SQLite с текстом ошибки в `iiko_error`.

Касса должна быть онлайн для облака (`/api/1/terminal_groups/is_alive`). В iikoWeb → Cloud API → Организации монитор кассы должен быть зелёным; 8 окт. помог перезапуск iikoFront.

## Защита от глупостей

Три простых правила, без авторизации гостей.

- Ограничение частоты: не больше одного заказа в 10 секунд от одного гостя (стол + имя), простой словарь в памяти. За одним столом заказывают несколько человек, поэтому лимит не на весь стол.
- Токена стола достаточно, гости не логинятся.
- Ключ бариста длинный и случайный, ссылку держишь только у себя.

## Деплой

На сервере, из папки с проектом: `sudo ./deploy/deploy.sh <домен> <email> --ssh-key "$(cat ~/.ssh/id_ed25519.pub)"` (ключ — с ноутбука). Перед этим A-запись домена должна смотреть на сервер. Обновление: подтянуть код и запустить скрипт ещё раз.

- Код копируется в `/opt/iikoweb`; там же `.env` и `data/` (база, фото) — при обновлении не трогаются.
- `.env` при первом запуске: ключи iiko берутся из `.env` рядом с кодом или спрашиваются; `BAR_KEY` и `MASTER_PASSWORD` генерируются новые; `BASE_URL=https://<домен>`, `IIKO_SEND_ORDERS=true`.
- SSH: ключ добавляется в `authorized_keys`, вход по паролю выключается только если ключ на месте (`/etc/ssh/sshd_config.d/10-iikoweb.conf`). Не закрывать сессию, пока не проверен вход по ключу.
- ufw: снаружи открыты только SSH, 80 и 443.
- Приложение в Docker, порт опубликован только на `127.0.0.1:8000` — Docker обходит ufw, поэтому привязка к localhost обязательна. В контейнере не root.
- nginx перед ним: HTTPS через `certbot --nginx`, запросы по IP и на чужие домены закрываются (`return 444`), лимит 10 запросов/с на `/api/`, в логах без query-строки (там ключ бариста).
- В конце скрипт показывает, что слушает снаружи, и предупреждает о лишнем; печатает ссылку бариста и мастер-пароль.
- QR-коды печатаются со страницы бариста кнопкой «QR-коды» по мастер-паролю.
- Меню, фото (сжатые в WebP) и модификаторы подтягиваются из iiko сами раз в `MENU_SYNC_MINUTES` (15 мин) и при старте.

## Чек-лист перед гостями

Прогнать целиком до прихода первого гостя.

- [ ] Каждый QR открывает правильный стол; проверить с телефона через мобильный интернет, а не по Wi-Fi.
- [ ] Касса онлайн: на странице бариста зелёное «касса онлайн».
- [ ] Заказ с трёх телефонов одновременно, все три сразу на кассе, у гостей номера iiko совпадают с iikoFront.
- [ ] Заказ с модификаторами (латте на миндальном + сироп ×2): состав и сумма на кассе верные.
- [ ] Стоп-лист: позиция пропадает у гостя после обновления страницы.
- [ ] Перезапустить сервис: гости видят свои заказы, они лежат в SQLite.

## Вне MVP

Онлайн-оплата, своя панель заказов у бариста (заказы ведут в iikoFront), модификаторы «С собой …» (скрыты), дозаказ в уже открытый заказ стола (`/api/1/order/add_items`), аккаунты гостей, история и аналитика.
